# IPU AI 보안필터 Risk Register Template

## 목적

이 문서는 `IPU AI 보안필터`의 제품, 기술, 사업, PoC 리스크를 구조적으로 관리하기 위한 템플릿이다.  
목표는 문제가 생길 때마다 반응적으로 처리하는 것이 아니라, 어떤 리스크가 있고 무엇을 먼저 줄여야 하는지 지속적으로 추적하는 것이다.

## 사용 원칙

- 리스크는 숨기지 않고 드러낸다.
- 추상적 불안보다 구체적인 위험으로 적는다.
- 영향도와 발생 가능성을 함께 본다.
- 대응 계획과 담당자를 같이 적는다.

## 권장 분류

- 제품 리스크
- 기술 리스크
- 세일즈/고객 리스크
- PoC 운영 리스크
- 조직/운영 리스크

## 카테고리별 예시

## 1. 제품 리스크

### 예시

- 고객이 제품을 단순 마스킹 툴로 오해할 수 있음
- 제품 정의가 너무 넓어져 범용 AI 앱처럼 보일 수 있음
- 수동 모드만으로는 가치 전달이 약하다고 느낄 수 있음

### 대응 예시

- 포지셔닝 문서와 데모 문구를 표준화
- PoC 범위를 실제 문제 중심으로 고정
- 문서와 발표자료에서 `보안 계층` 포지션을 반복

## 2. 기술 리스크

### 예시

- 탐지 정확도가 낮을 수 있음
- 복원 후 토큰이 남을 수 있음
- 문맥 유지형 치환 품질이 기대에 못 미칠 수 있음
- 정책별 동작 차이가 아직 약할 수 있음
- 세션 저장소가 메모리 기반이라 한계가 있음

### 대응 예시

- smoke test와 unit test 확대
- 실제 고객 샘플 기준 품질 점검
- 정책 분기와 설정 구조 고도화
- TTL, 설정 주입, 운영 로그 단계적 추가

## 3. 세일즈/고객 리스크

### 예시

- 초기 고객이 문제를 충분히 심각하게 느끼지 않을 수 있음
- 대기업/공공 세일즈 사이클이 길 수 있음
- 고객이 로컬 LLM 구축을 우선 선택할 수 있음
- 보안팀과 현업팀의 관점이 엇갈릴 수 있음

### 대응 예시

- Strong Fit 계정에 집중
- 작은 PoC로 진입
- 로컬 LLM 대비 포지션을 명확히 설명
- 보안팀과 현업팀을 동시에 미팅에 포함

## 4. PoC 운영 리스크

### 예시

- 범위가 너무 넓어질 수 있음
- 성공 기준 없이 진행될 수 있음
- 고객 샘플 문서 확보가 늦어질 수 있음
- PoC가 커스터마이징 프로젝트처럼 변할 수 있음

### 대응 예시

- 킥오프 때 범위와 성공 기준을 문서화
- 부서 1곳, 문서 1~2종 원칙 유지
- 중간 리뷰를 필수로 운영

## 5. 조직/운영 리스크

### 예시

- 사업 문서와 개발 상태가 어긋날 수 있음
- 우선순위가 기술 호기심 쪽으로 쏠릴 수 있음
- 반복 설명이 대표 개인에게 과도하게 집중될 수 있음

### 대응 예시

- 문서 인덱스와 상위 로드맵 유지
- 월간 board update 작성
- FAQ, founder talking points, one-pager 재활용

## 영향도/가능성 기준 예시

### 영향도

- 높음:
  - 고객 신뢰, PoC 성사, 핵심 기능에 직접 타격
- 중간:
  - 일정 지연이나 품질 저하를 유발하지만 우회 가능
- 낮음:
  - 불편은 있으나 전체 흐름에는 큰 영향이 없음

### 가능성

- 높음:
  - 이미 드러났거나 반복 가능성이 큼
- 중간:
  - 특정 조건에서 발생 가능
- 낮음:
  - 현재 기준으로는 가능성이 낮음

## 운영 주기

- 주간:
  - 새로운 리스크 등록
- 월간:
  - 영향도/가능성 재평가
- 분기:
  - 닫힌 리스크와 새 리스크 비교

## 리스크 관리 시 주의사항

- 모든 것을 리스크로 적지 않는다.
- 실제 의사결정에 영향을 주는 것만 남긴다.
- 대응 계획 없는 리스크는 의미가 약하다.
- 해결됐으면 닫고, 재발 가능성이 있으면 다시 연다.

## 결론

좋은 리스크 레지스터는 불안을 늘리는 문서가 아니라, `무엇이 진짜 위험이고 무엇을 먼저 해결해야 하는지`를 선명하게 만드는 문서다.  
IPU AI 보안필터는 기술과 세일즈가 같이 움직이는 제품이므로, 두 축의 리스크를 함께 관리해야 한다.
