# 27. Multi-Speaker And Meeting Audio Policy

## 목적

이 문서는 현재 IPU manual-preview 음성 입력에서 다화자 음성과 긴 회의 녹음을 어떻게 다룰지 운영 기준을 고정한다.

## 현재 결론

지금 단계에서는 다화자 분리, 화자 라벨링, 회의 녹음 전체본 처리를 기본 지원으로 두지 않는다.

현재 음성 입력이 책임지는 범위는 아래다.

- 짧은 음성 파일 업로드
- 단일 전사 텍스트 생성
- 전사 텍스트 기준 민감정보 치환

즉 현재는 "누가 말했는지"보다 "전사 텍스트에 민감정보가 있는지"까지만 본다.

## 왜 지금 보류하는가

### 1. 현재 전사 품질도 아직 보수적으로 봐야 한다

짧은 한국어 샘플에서도 Whisper 결과가 흔들린다.  
이 상태에서 다화자나 회의 녹음까지 기본 지원으로 말하면 제품 메시지가 과장된다.

### 2. 회의 녹음은 길이 문제와 화자 문제를 동시에 가진다

회의 녹음 전체본은 보통 아래 문제를 함께 가진다.

- `1분 이상` 긴 길이
- 여러 화자
- 중간 잡음
- 겹침 발화
- 이름, 직함, 연락처, 금액 같은 민감정보 혼합

즉 긴 음성 정책과 다화자 정책이 같이 움직여야 한다.

### 3. 현재 manual-preview 핵심과 거리가 있다

현재 제품 핵심은 "민감정보 탐지 / 치환 / 복원"이다.  
회의록 정리, 화자 분리, 자막 편집은 이후 확장 가치가 있을 수 있지만 지금 MVP 핵심은 아니다.

## 현재 운영 기준

### 데모에 써도 되는 범위

- 단일 화자 위주의 짧은 음성
- 화자 구분이 필요 없는 간단한 발화
- "음성을 전사하고 민감정보를 가린다"는 흐름 시연

### 기본 지원으로 말하면 안 되는 범위

- 회의 녹음 전체본
- 인터뷰 원본 전체본
- 두 명 이상 발화가 섞인 녹음
- 화자별 분리 결과
- 화자 라벨 기반 리포트
- 회의록 자동 정리

## 사용자 안내 기준

- 회의 녹음은 현재 기본 경로로 권장하지 않는다.
- 여러 화자가 섞인 녹음은 가능한 한 발화 단위로 나눠서 올리도록 안내한다.
- 실제 사용은 짧고 비교적 단일 화자에 가까운 구간부터 검토하도록 유도한다.

## backend / frontend 기준

### backend

- audio route 는 단일 plain text 전사만 반환 대상으로 본다.
- 화자 분리 정보, diarization 결과, speaker label은 현재 다루지 않는다.

### frontend

- 화자 카드, 발화자별 타임라인, 회의록 전용 UI는 열지 않는다.
- 현재 결과 화면은 전사 텍스트와 치환 결과 중심으로 유지한다.

## 향후 승격 조건

아래가 확보되기 전까지는 다화자/회의 녹음을 기본 지원으로 승격하지 않는다.

1. 다화자 품질 샘플셋
2. diarization 또는 speaker-label 전략
3. 긴 회의 녹음 속도/메모리 기준
4. 화자별 민감정보 치환 UX 설계
5. 회의 녹음 전용 검증선

## 권장 다음 확장 순서

1. 긴 음성 전용 검증선 분리 여부 결정
2. 필요 시 debug-only diarization 후보 조사
3. 회의 녹음 샘플셋 확보
4. 그 다음에만 화자별 결과 UI 검토

현재 긴 음성 검증선 기준은 [`28-long-audio-verification-policy.md`](./28-long-audio-verification-policy.md) 를 따른다.
debug-only diarization 후보 기준은 [`29-debug-diarization-candidates.md`](./29-debug-diarization-candidates.md) 를 따른다.
회의 녹음 샘플셋 기준은 [`30-meeting-audio-sample-set-policy.md`](./30-meeting-audio-sample-set-policy.md) 를 따른다.

## 현재 결론

현재 IPU manual-preview 음성 입력은 짧은 단일 화자 샘플 중심으로 운영한다.  
다화자 음성과 회의 녹음 전체본은 아직 기본 지원이 아니라 별도 확장 과제로 유지한다.
